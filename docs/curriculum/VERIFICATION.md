# Syllabus verification

The owner asked whether the syllabus a learner gets is accurate for their class. This is the
row-by-row answer, produced by `wobo_gateway.curriculum.discovery.audit` on 2026-09-05 against
`content/curriculum/syllabi/`. Every count and every verdict below is read out of the files and
the sources; the table between the two `generated` markers is regenerated by the pass, and the
prose around it is a reading of that table. A wrong row here says it is wrong.

## The short answer

- **121 files. 71 of them hold no syllabus at all.** They are stored negative results: the
  board's portal needs a browser (Karnataka, Maharashtra, Telangana), the board publishes no
  document for that class (Andhra Pradesh, ICSE classes 6 to 8), or the document is not machine
  readable (NIOS English). For those boards and classes the question "is it accurate" has no
  object: in the product, picking that board and class yields no syllabus.
- **50 files hold units read off the board's own document.** All 41 source documents they cite
  were re-fetched on 2026-09-05 and every one hashed byte-for-byte identical to what the build
  recorded. 34 came over urllib; the 7 NIOS PDFs came by curl, because `nios.ac.in` serves a
  certificate chain this machine's Python cannot build while the system trust store can. The
  transport is written into each file's provenance.
- **15 files are now `verified`.** Every unit and topic name in them was found in the source at
  the place it cites (or within a page of it), the counts match the document's own numbering or
  the second reader agreed, and nothing else failed. Ten were decided by code alone, five with
  the second reader. Verified: CBSE 9 to 12 mathematics, 9 and 10 science, 11 and 12 biology,
  11 chemistry, 11 and 12 physics; NIOS 10 mathematics, 10 social science, 12 biology, 12
  mathematics, 12 physics.
- **Verified is not the same as right, and a second reading the same day found four things in
  verified files that the checks cannot see.** The checks ask whether every name is in the
  source; they do not read what the file says *about* a name. So `cbse/class-10-science.json`
  passed with three topics marked "assessed only formatively" that the document examines (Acids,
  Bases and Salts; the human eye; the prism): the first cut had read a one-space indent in the
  text layer as the document's formative box, and page 6 of that text layer is indented whole.
  Read off the rendered pages, the boxes hold exactly three topics (Periodic Classification of
  Elements, Evolution, and Motor, Electromagnetic Induction, Electric Generator) and the Note for
  Teachers on page 6 names what is not examined; the file now says that, cites the physical
  pages (4 to 6, not 6 to 8), records the document's own unresolved "Heredity and Evolution"
  against Heredity, and holds by code alone with every citation on its page. `cbse/class-11-
  physics.json` and `class-12-physics.json` recorded one unit's marks as the figure the table
  prints for a bracketed group (Kinematics 23, Thermodynamics 20) and left the group's other
  units at null; every unit now carries `marks_group`, the bracket and its figure, and no figure
  of its own. `nios/class-12-mathematics.json` carried the document's misprint "Module- ll" as
  unit number "LL"; it is II. Each correction was made in the source reading (the builders under
  `tools/extract`), re-run through this pass, and is held by `tests/test_curriculum_readings.py`.
  The pass itself had a defect the same file exposed: `apply()` only ever appended to
  `checks_failed`, so a check that failed on one run and passed on the next stayed listed as
  failed under a `verified` label. It now replaces its own check names run by run.
- **20 CISCE files are `provisional`, incomplete.** Every unit name holds against the booklet,
  but every unit has `topics: null` (the topic layer was withdrawn on 2026-09-03 for filing
  topics under the wrong units), so a learner who opens a unit finds nothing under it. A unit
  list that is right is not a syllabus that is whole, and this pass does not call it verified.
- **15 files are `provisional`, flagged**, each with a `status_reason` naming exactly what failed.
  Three failed in code, twelve on the second reader's reading. They are itemised below, with my
  own re-reading of the source where the reader's objection needed one.

**Nothing was written to production.** This pass changes files under `content/curriculum/`
and this document. `curriculum.frameworks`, `versions` and `nodes` in Supabase were not touched
by it and hold what they held before.

## What the pass did, and what it cost

For each of the 50 files with units: fetch the recorded source, hash it against the build,
then look for every unit and topic name on the page it cites, in code and with no model. A name
verbatim on its page, or verbatim elsewhere in the document, is proof. A name found only as a
run of words across a table column, as a composite whose parts sit on or beside the cited page,
as every word scattered within a page of the citation, or a unit whose own name is nowhere but
whose every chapter is verbatim on the page (a container the build named after the book), is
evidence for a second reader, never proof. A name found nowhere fails the file. Coverage is
read off the document's own numbering on the cited pages; where the numbering fits the file
exactly the check passes, where it shows a chapter the file lacks the check fails and names it,
and where the pages number nothing code can count the question goes to the second reader.

The second reader ran only on files code could not decide: 22 calls over 18 files, 155,066
prompt tokens, 4,141 completion tokens, **USD 0.36** against a USD 10 cap. Every call was
answered by `gpt-5.6-terra`. The verify tier's primary, Claude Opus 5, refused every call with
"Your credit balance is too low to access the Anthropic API", and the router's fallback chain
answered instead; the model that actually read each file is recorded in its provenance, never
the one the policy asked for. Gemini, the third link in the chain, was reachable only because
this run aliased `GOOGLE_AI_API_KEY` to the `GEMINI_API_KEY` litellm reads; the gateway itself
does not, which is an open item below.

A first live run the same morning cost nothing and decided nothing: the call bypassed
`model_call`, `gpt-5.6-terra` refused `temperature=0.0`, and litellm reported the last failure in
the chain, so all 22 files came back "second reader unreachable". The pass and discovery's
`tier_complete` now go through `model_call.complete`, which drops the refused knob and retries;
a test holds them there.

## What `verified` means here

A verified file says: every name in it is the document's, at or within a page of the place the
file cites; the document's own numbering, where it has one, matches the file's count; and the
source on the board's host today is byte-for-byte the one the build read. It does not say that
two learners or the owner have used the file without structural edits (`docs/CURRICULUM.md`
section 4.5's other route to verified); the brief for this pass authorised promotion on the
pass alone. It does not say the file goes deeper than its source: where the source is a Contents
page, the file's topics are chapters and carry no objectives, because the page states none.

## How to read the table

- **Status** is the file's `status` after the pass, with the reason class: verified;
  provisional, failed (a check failed or the second reader disagreed); provisional, incomplete
  (units hold, no topic layer); provisional, no units to check (a blocked file).
- **Source** names each cited document and whether today's bytes hash to the build's record.
- **Checked** counts how each name was found, strongest grade first, then the coverage verdict
  per document, then the second reader's verdict where it was asked.
- **Failed or open** is the `status_reason` written into the file, or, on a verified row, any
  check that failed without blocking (a citation more than one page off is recorded, never
  hidden).
